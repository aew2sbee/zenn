### 📌 IPの役割としくみとは？
IP（Internet Protocol）は、データを宛先のホストまで届ける役割を持つプロトコル。ホストとは、PCやサーバーなど IP で通信する機器のこと。ルーターは、ネットワークとネットワークをつなぐ装置のこと。郵便に例えると、IPアドレスが住所、IPパケットが封筒、ルーターが郵便局にあたる。

![ネットワークA・B・Cの境目にルーターが立ち、ネットワークA内の送信元ホスト（PC）が宛先と送信元のIPアドレスを書いたIPパケットを封筒のようにルーター1に出し、ルーター1がルーティングテーブルで宛先を見てルーター2へ中継し、ルーター2が宛先ホスト（Webサーバー）に届ける流れと、郵便とIPの用語の対応を示した図](/images/books/book-record-of-reading/book066-ip-postal.drawio.png)

:::details 🤖 Claude に相談した内容
**郵便とIPの対応**

| 郵便 | IP |
| --- | --- |
| 家（差出人・宛先） | ホスト（IP で通信する機器。PC やサーバーなど） |
| 住所 | IPアドレス |
| 封筒 | IPパケット |
| 封筒の宛名（宛先・差出人） | IPヘッダー（宛先IP・送信元IP） |
| 手紙の中身 | データ |
| 町（地域） | ネットワーク |
| 郵便局（町と町をつなぐ） | ルーター（ネットワーク同士をつなぐ装置） |
| 郵便局の配送ルール | ルーティングテーブル |
| 普通郵便（届いたか確認しない） | ベストエフォート（届く保証をしない） |

**IP でデータが届くまでの流れ**

1. 送信元ホストは、送りたいデータに IPヘッダーを付けて IPパケットを作る。IPヘッダーには宛先IPアドレスと送信元IPアドレスが書かれている。封筒に手紙を入れて宛名を書くのと同じ。
2. 送信元ホストは、IPパケットを近くのルーターに渡す。郵便ポストに投函するイメージ。
3. ルーターは宛先IPアドレスだけを見て、ルーティングテーブルから次に渡す相手を決めて中継する。郵便局が宛先の住所を見て、次の郵便局へ送るのと同じ。
4. 中継を繰り返し、宛先のネットワークにつながるルーターが IPパケットを宛先ホストに届ける。

- ルーターは複数のネットワークにまたがって置かれ、ネットワーク同士をつなぐ。同じネットワークの中なら直接届けられるが、別のネットワークのホストに送るときはルーターを経由する必要がある。町の中の配達は近所で済むが、別の町へ送るには郵便局を通すのと同じ。
- 各ルーターは最終的な宛先までの道のりをすべて知っているわけではなく、「次に誰に渡すか」だけを知っている。これをバケツリレーのように繰り返して届ける。
- IP は届けることに専念し、届いたかの確認や、失われたパケットの再送はしない。これをベストエフォートという。確実に届ける必要がある通信では、上の層の TCP が確認と再送を担当する。

参考: https://www.rfc-editor.org/rfc/rfc791
:::

### 📌 ペイロードとは？
ペイロードは、宛先などの制御情報（ヘッダー）を除いた、運びたい中身のデータのこと。API の HTTP リクエストでいうボディにあたる。郵便に例えると、封筒の宛名がヘッダー、中の手紙がペイロード。

:::details 🤖 Claude に相談した内容
**どの層から見たペイロードかで中身が変わる**

ネットワークでは、データは外側の層のヘッダーで包まれて送られる。

```
[IPヘッダー][TCPヘッダー][HTTPヘッダー][HTTPボディ]
```

| 見ている層 | ペイロードにあたる部分 |
| --- | --- |
| HTTP | HTTPボディ（API の body と同じ） |
| TCP | HTTPヘッダー＋HTTPボディ |
| IP | TCPヘッダー＋HTTPヘッダー＋HTTPボディ |

- IP にとっては、TCP や HTTP のヘッダーも含めて全部が中身の手紙になる。IP はペイロードの中身を見ずに、自分のヘッダーにある宛先IPアドレスだけを見て運ぶ。
- 上の「IPの役割としくみとは？」の図で「データ（＝手紙の中身）」と書いた部分が、IP のペイロードにあたる。
:::

### 📌 TCPとは？
TCP（Transmission Control Protocol）は、最初から最後まですべてのデータが、順序どおりに正しく届くように制御するプロトコル。IP は届く保証をしないため、その上で TCP が確認や再送を行い、確実に届ける。

![送信元ホスト（PC）と宛先ホスト（Webサーバー）の間で、①SYN・SYN+ACK・ACKの3ウェイハンドシェイクで準備を確かめ合い、②番号付きでデータ1〜3を送り、途中で消えたデータ2を返事が来ないため再送し、受信側が届いた順1→3→2をシーケンス番号で1→2→3に並べ直す流れを示した図](/images/books/book-record-of-reading/book066-tcp-postal.drawio.png)

:::details 🤖 Claude に相談した内容
**IP と TCP の役割分担**

| | IP | TCP |
| --- | --- | --- |
| 役割 | 宛先のホストまでパケットを運ぶ | データを順序どおりに漏れなく届ける |
| 届いたかの確認 | しない（ベストエフォート） | する（届かなければ再送する） |
| 郵便に例えると | 普通郵便 | 番号を振った書留を、受け取りの返事をもらいながら送る |

**順序どおりに正しく届けるためのしくみ**

- **コネクションの確立:** データを送る前に、送信側と受信側で「これから送ります」「どうぞ」とやり取りして、通信の準備をする。3回のやり取りで行うので、3ウェイハンドシェイクと呼ぶ。
- **シーケンス番号:** 送るデータに通し番号を付ける。途中で順番が入れ替わって届いても、受信側は番号を見て元の順番に並べ直せる。
- **確認応答（ACK）と再送:** 受信側は「ここまで受け取った」と返事（ACK）を返す。送信側は、一定時間たっても返事がないデータを送り直す。
- **チェックサム:** データが途中で壊れていないかを確認する。壊れていたら捨てて、再送してもらう。
- **フロー制御:** 受信側が処理しきれる量に合わせて、送る量を調整する。

- Web ページの表示やファイルの転送のように、1バイトでも欠けたり順番が狂ったりすると困る通信で使われる。
- 確認や再送のぶん、届くまでに時間がかかることがある。多少欠けても速さを優先したい動画の配信や音声通話などでは、確認をしない UDP が使われることが多い。

参考: https://www.rfc-editor.org/rfc/rfc9293
:::

### 📌 TCPのバッファとは？
バッファは、データを一時的にためておくメモリ上の置き場所のこと。TCP で通信する両端のホストは、OS がメモリ上に送信バッファと受信バッファを確保し、そこにデータを出し入れしながら送受信を管理している。途中のルーターは TCP のバッファを持たない。

![送る側のWebサーバーの送信バッファにACK済みの1、再送用に残した2、ACK待ちの3、未送信の4があり、ルーターはIPの宛先を見て中継するだけで、受け取る側のPCの受信バッファには1と3が届いて2を待ち、番号順にそろってからブラウザに渡し、PCはACKで受信バッファの空きを伝えて送る量を調整してもらう様子を示した図](/images/books/book-record-of-reading/book066-tcp-buffer.drawio.png)

:::details 🤖 Claude に相談した内容
**送信バッファと受信バッファ**

郵便に例えると、送信バッファは差出人の家の「発送待ちの棚」、受信バッファは宛先の家の「郵便受け」にあたる。

| | 送信バッファ（＝発送待ちの棚） | 受信バッファ（＝郵便受け） |
| --- | --- | --- |
| 持っている機器 | 送る側のホスト | 受け取る側のホスト |
| 入れるもの | アプリが「送って」と渡したデータ | 届いたデータ |
| 役割 | ACK が来るまでデータを残し、届かなければ再送する | 順番が入れ替わって届いたデータを待たせ、番号順にそろえてアプリに渡す |
| 消すタイミング | ACK が来たとき | アプリが読み出したとき |

- バッファは OS が TCP の接続ごとにメモリ上に確保する。アプリはバッファにデータを渡したり、バッファから読み出したりするだけでよく、再送や並べ直しは OS の TCP が受け持つ。
- TCP は双方向に通信するので、実際には両方のホストが送信バッファと受信バッファの両方を持っている。ブラウザがリクエストを送るときは、PC の送信バッファとサーバーの受信バッファが使われる。

**ルーターは TCP のバッファを持たない**

- ルーターは IP ヘッダーの宛先IPアドレスを見て中継するだけで、TCP のヘッダーやデータは IP のペイロードとしてそのまま運ぶ。そのため、確認・再送・並べ直しは両端のホスト同士で行う。
- ルーターにも、混雑したときにパケットを一時的に並べて待たせるバッファ（キュー）はある。ただし中継の順番待ちのための場所で、TCP のバッファとは別物。キューがあふれるとパケットが捨てられ、TCP の再送が必要になる。

**例: PC のブラウザでサーバーから画像（3MB）をダウンロードする**

1. サーバーの Web サーバーソフト（nginx など）が画像を TCP に渡し、TCP は送信バッファに入れる。ソフトはすぐ次の仕事に移れる。
2. TCP は送信バッファから小分けに取り出し、番号を付けて送る。送ったデータも ACK が来るまでは残しておく。
3. 途中のルーターが混雑していて、「2」が捨てられる。
4. PC の受信バッファには「1」と「3」が届き、「3」は「2」を待つ。PC は「1 まで受け取った。次は 2 をください」と ACK を返す。
5. サーバーは送信バッファに残しておいた「2」を再送する。
6. 「2」が届くと受信バッファで「1 → 2 → 3」がそろい、ブラウザが読み出して画像を表示する。

**バッファの空きを伝えて送る量を調整する（フロー制御）**

- 受信バッファの大きさには限りがある。受け取る側は ACK と一緒に「受信バッファの空きはあと○○バイト」と伝える。
- ブラウザの読み出しが遅れて空きが少なくなると、送る側は空きを超えないように送る量を減らして待つ。これで、受け取る側があふれてデータを取りこぼすのを防ぐ。

参考: https://www.rfc-editor.org/rfc/rfc9293
:::

### 📌 ACKとは？
ACK（Acknowledgement）は「確認応答」のことで、受け取る側が送る側に「ここまで受け取りました」と返す返事。郵便に例えると、書留の受け取りの返事にあたる。TCP は ACK が来たかどうかで、データが届いたかを判断する。

![左は、データ2が途中で消えたあとデータ3〜5が届くたびに受け取る側が同じACK 2を返し、同じACKが何度も来たので送る側がタイムアウトを待たずにデータ2を再送し、1〜5がそろってACK 6が返る高速再送の流れ。右は、データ1が消えてACKが来ないまま一定時間たち、タイムアウトでデータ1を再送してACK 2が返る流れを示した図](/images/books/book-record-of-reading/book066-tcp-ack.drawio.png)

:::details 🤖 Claude に相談した内容
**ACK番号は「次に欲しいデータの番号」**

ACK には ACK番号が入っている。これは受け取ったデータの番号ではなく、次に欲しいデータの番号。

| 受け取り済みのデータ | ACK番号 | 意味 |
| --- | --- | --- |
| 1 | 2 | 次は 2 をください |
| 1, 3（2 がない） | 2 | まだ 2 を待っています |
| 1, 2, 3 | 4 | 3 までは全部届いた。次は 4 をください |

- ACK番号は「ここまでは途切れずに全部受け取った」という意味を持つ。ACK番号が 4 なら 1〜3 が全部届いたと分かるので、1つずつ返事をしなくてもまとめて確認できる。

**ACK を使った再送**

送る側は ACK の来かたで「届いていない」ことに気づき、送信バッファに残しておいたデータを送り直す。

| 気づき方 | 状況 | 例えると |
| --- | --- | --- |
| 重複 ACK（高速再送） | 「まだ 2 を待っています」という同じ ACK が何度も届く | 「2 がない」と何度も言われるので、時間切れを待たずにすぐ送り直す |
| タイムアウト | 送ってから一定時間たっても、そのデータの ACK が来ない | 返事が来ないので送り直す |

- 高速再送は、同じ ACK が3回重なる（重複 ACK が3つ届く）と行われる。タイムアウトまで待たなくてよいので、早く立ち直れる。
- タイムアウトは、送った最後のデータが消えたときなど、後ろに続くデータがなくて重複 ACK が起きない場合にも働く。

**例: 「ACK 4」を返したあと、4 が届かない場合**

どの番号が消えても同じルールで送り直す。ただし、4 の後ろにまだデータが続くかどうかで、気づき方が変わる。

- 4 の後ろにデータが続く場合は、高速再送になる。

| 届いたデータ | 受け取る側が返す ACK |
| --- | --- |
| 1, 2, 3 | ACK 4「次は 4 をください」 |
| 5（4 は消えた） | ACK 4「まだ 4 を待っています」 |
| 6 | ACK 4（同じ返事） |
| 7 | ACK 4（同じ返事） |

同じ ACK 4 が何度も来るので、送る側はタイムアウトを待たずに 4 を送り直す。4 が届くと 4〜7 がそろい、受け取る側は「ACK 8」を返す。図の①と同じ流れ。

- 4 が最後のデータの場合は、タイムアウトになる。4 の後ろに何も届かないので、受け取る側は ACK を返すきっかけがなく、重複 ACK が起きない。送る側は一定時間待ってから 4 を送り直す。図の②と同じ流れ。
- 4 は届いたのに、ACK のほうが消えることもある。ACK も IP で運ばれるので、途中で消えることがあるため。
  - その後に「ACK 5」や「ACK 6」が届けば、ACK番号は「ここまで全部受け取った」という意味なので、送る側は 4 も届いたと分かる。
  - 後ろの ACK も届かなければ、送る側はタイムアウトで 4 を送り直す。受け取る側は 4 を二重に受け取るが、番号で重複に気づいて捨て、もう一度 ACK を返す。

**ACK はほかの情報も運ぶ**

- 受信バッファの空き: 「空きはあと 8KB です」のように、受信バッファの空きを一緒に伝える。送る側はこれを見て送る量を調整する（フロー制御）。
- 3ウェイハンドシェイクの SYN+ACK の ACK も同じ確認応答で、「接続していいですか？」（SYN）を受け取ったという返事になっている。

**補足: 実際の番号はバイト単位**

これまでの図では分かりやすさを優先して 1, 2, 3 と番号を付けたが、実際の TCP はデータ1バイトごとに番号（シーケンス番号）を数える。たとえば 1000 バイトのデータを受け取ったら、ACK番号は「次は 1001 バイト目をください」のような値になる。考え方は同じ。

参考: https://www.rfc-editor.org/rfc/rfc9293

参考: https://www.rfc-editor.org/rfc/rfc5681
:::

### 📌 UDPとは？
UDP（User Datagram Protocol）は、届いたパケットに含まれるデータが破損していないことを確かめる機能だけを持つ、シンプルなプロトコル。TCP のような確認応答（ACK）、再送、並べ直しはしない。そのぶん手順が少なく、速く送れる。

UDP に適しているのは、次のようなケース。

- 1200 バイト程度の小さなデータを送りたい
- パケットが抜けたら、それを飛ばして通信を続けたい
- 送ったデータの塊を、受信側でそのまま（塊のまま）受け取りたい
- 1秒単位や1ミリ秒単位など、定期的に小さいデータを送りたい
- 帯域が保証された回線を占有して、高品質な通信を行いたい
- IPアドレスが変わる環境でも、通信（コネクション）を維持したい

![接続の準備なしでデータ1〜5を送り、受け取る側はチェックサムが合ったデータ1・3・5をすぐアプリに渡し、途中で消えたデータ2は誰も気づかず再送もせず、途中で壊れたデータ4はチェックサムが合わないので捨て、2と4を飛ばして通信を続ける様子と、TCPなら2の再送を待って3以降も止まることとの比較を示した図](/images/books/book-record-of-reading/book066-udp.drawio.png)

:::details 🤖 Claude に相談した内容
**データが破損していないかの確認（チェックサム）**

- 送る側は、データから計算した値（チェックサム）を UDP ヘッダーに入れて送る。
- 受け取る側は同じ計算をして、チェックサムと一致するかを確かめる。一致しなければ、途中でデータが壊れたと判断してパケットを捨てる。
- 郵便に例えると、届いた手紙が破れていたら読まずに捨てるイメージ。差出人に「届かなかった」とは知らせないし、送り直してもらうこともない。

**注意: 保証するのは「届いたデータが壊れていないか」まで**

- 壊れたパケットは捨てるだけなので、アプリから見るとそのパケットは届かなかったことになる。届くこと自体や、届く順番は保証しない。
- IPv4 では、送る側がチェックサムを使わない設定（値を 0 にする）にもできる。IPv6 ではチェックサムが必須。
- チェックサムは簡単な計算なので、まれに壊れたデータを見逃すこともある。確実性が必要な場合は、アプリ側で別の確認を組み合わせる。

**UDP に適しているケースの理由**

| ケース | UDP が向いている理由 | 例 |
| --- | --- | --- |
| 1200 バイト程度の小さなデータ | 1つのパケットに収まるので、分割や並べ直しがいらない。TCP の接続の準備（3ウェイハンドシェイク）のほうが、データより手間がかかってしまう | DNS の問い合わせ |
| パケットが抜けたら飛ばしたい | TCP は抜けたデータの再送を待つあいだ、後ろのデータも渡さずに止まる。UDP は届いたものから順にすぐ使える | 音声通話、ビデオ会議、オンラインゲーム |
| データの塊をそのまま受け取りたい | UDP は送った1回分のデータが、そのまま1つの塊として届く。TCP はデータを区切りのない連続したバイトの流れとして扱うので、どこまでが1つのメッセージかをアプリ側で区切る必要がある | ゲームの操作情報、センサーの測定値 |
| 定期的に小さいデータを送る | 次のデータがすぐ来るので、古いデータを再送しても意味がない。再送待ちで新しいデータが遅れるほうが困る | 時刻同期（NTP）、センサーの定期送信、死活監視 |
| 帯域保証された回線を占有して高品質に送る | TCP は混雑を感じると送る量を自動で減らす（輻輳制御）。帯域が保証された専用の回線なら減らす必要がないので、UDP で一定の速さで送り続けられる | 放送局の映像伝送、専用線での映像配信 |
| IPアドレスが変わってもコネクションを維持したい | TCP の接続は「送信元IP・送信元ポート・宛先IP・宛先ポート」の組で見分けるので、IPアドレスが変わると切れる。UDP は接続を持たないので、アプリ側で独自の ID を使って相手を見分ければ、IPアドレスが変わっても通信を続けられる | QUIC（HTTP/3）、WireGuard（VPN）、Wi-Fi とモバイル回線の切り替え |

- 1200 バイトは、多くのネットワークで分割されずに1つのパケットで届くと見込める大きさの目安。IPv6 では、どの経路でも 1280 バイトのパケットが通ることが決まっているので、ヘッダーの分を引いて 1200 バイト程度に収めることが多い。
- 帯域保証のない共有の回線で UDP を使って大量に送り続けると、送る量を減らさないぶん回線を占有して、ほかの通信を邪魔することがある。そのため、帯域が保証された回線のほうが向いている。

**TCP と UDP の比較**

| | TCP | UDP |
| --- | --- | --- |
| 事前の接続（3ウェイハンドシェイク） | する | しない |
| 届いたかの確認（ACK）と再送 | する | しない |
| 順番の並べ直し | する | しない |
| データが破損していないかの確認 | する（チェックサム） | する（チェックサム） |
| 速さ | 確認や再送のぶん遅くなることがある | 手順が少なく速い |
| 主な用途 | Web ページ、ファイル転送、メール | 動画配信、音声通話、オンラインゲーム、DNS |

- 動画や音声通話では、少し欠けても再送を待って遅れるより、次のデータを早く届けたほうがよい。そのため UDP が使われることが多い。
- DNS のように小さなデータを1回やり取りするだけの通信も、接続の準備がいらない UDP が向いている。届かなければ、アプリ側でもう一度問い合わせる。

参考: https://www.rfc-editor.org/rfc/rfc8200

参考: https://www.rfc-editor.org/rfc/rfc9000

### 📌 よく使われるポート番号と区分とは？
ポート番号は、1台のホストの中で通信相手のアプリを見分けるための番号。IPアドレスで宛先のホストまで届け、ポート番号でそのホストのどのアプリに渡すかを決める。サーバー側のアプリが待ち受けるポート番号は、サービスごとに慣習として決まっている。

| サービス | ポート番号 | プロトコル | 用途 |
| --- | --- | --- | --- |
| SSH | 22 | TCP | 暗号化したリモートログイン |
| DNS | 53 | UDP / TCP | 名前解決 |
| DHCP | 67（サーバー）/ 68（クライアント） | UDP | IPアドレスの自動割り当て |
| HTTP | 80 | TCP | Web 通信（暗号化なし） |
| HTTPS | 443 | TCP（HTTP/3 は UDP） | 暗号化した Web 通信 |

| 区分 | 範囲 | 説明 |
| --- | --- | --- |
| ウェルノウンポート | 0〜1023 | 代表的なサービス用に予約されている番号 |
| 登録済みポート | 1024〜49151 | 特定のアプリケーション用に IANA に登録されている番号 |
| 動的・プライベートポート | 49152〜65535 | クライアントが通信するときに一時的に割り当てられる番号 |

:::details 🤖 Claude に相談した内容
**ポート番号は自由に決められるのに、なぜよく使う番号を決めているのか**

ポート番号は技術的には自由に決められる。SSH を 2222 番で動かしても、Web サーバーを 8080 番で動かしても通信できる。それでも番号を決めておくのは、通信を始める側が、相手のポート番号を事前に知っていなければならないから。

- クライアントがサーバーに接続するときは、宛先として「IPアドレス」と「ポート番号」の両方を指定する。
- IPアドレスは DNS で調べられるが、ポート番号には一般的に調べる仕組みがない。
- そこで「Web なら 80 番」「SSH なら 22 番」のように、IANA（インターネットの番号を管理する組織）が共通の番号を決めている。

`https://example.com` のようにポート番号を書かなくてもアクセスできるのは、ブラウザが「HTTPS なら 443 番」という取り決めに従って補っているから。それ以外の番号で動いているサーバーには、`http://localhost:8000` のように番号を明示する。

**クライアント側のポート番号は決めなくてよい**

1. クライアントが送る通信には「送信元ポート番号」が入っている。
2. サーバーはその送信元ポート番号宛てに返信する。

サーバーは届いた通信を見れば返信先が分かるので、クライアント側の番号は事前に決めておく必要がない。そのため OS が空いている番号を一時的に割り当てる。

| | ポート番号 | 決め方 |
| --- | --- | --- |
| サーバー側（待ち受ける側） | 固定（22、80、443 など） | 相手に知ってもらう必要があるので、慣習として決めておく |
| クライアント側（接続する側） | 毎回変わる（49152〜 など） | 返信先は通信の中に書かれているので、決めておく必要がない |

- よく使われるポート番号は技術的な制約ではなく、「事前に打ち合わせなくてもつながる」ようにするための約束事。番号を変えることもできるが、その場合は接続する側が番号を知っている必要がある。

**補足**

- DNS は、通常の問い合わせは UDP を使い、応答が大きい場合やゾーン転送（DNS サーバー間でのデータのコピー）では TCP を使う。
- 動的・プライベートポートの範囲は IANA の推奨で、実際に使う範囲は OS によって異なる。たとえば Linux は初期設定で 32768〜60999 を使う。
- ほかによく出てくるものに、FTP（20/21）、Telnet（23）、SMTP（25）、POP3（110）、NTP（123）、IMAP（143）がある。

参考: https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml

参考: https://www.rfc-editor.org/rfc/rfc6335
:::

### 📌 ICMPとは？
ICMP（Internet Control Message Protocol）は、IP を制御するための情報を伝える取り決め（プロトコル）。IP はパケットが届かなくても送信元に知らせないため、ICMP が「宛先に届かなかった」などのエラーや、通信の状態を送信元に伝える。郵便に例えると、宛先が見つからずに差し戻されるときに貼られる「あて所に尋ねあたりません」の付箋にあたる。

:::details 🤖 Claude に相談した内容
**ICMP が必要な理由**

- IP はベストエフォートで、パケットが途中で捨てられても送信元に何も伝えない。
- それでは送信元は「なぜ届かないのか」が分からない。そこで、途中のルーターや宛先のホストが ICMP のメッセージで理由を送り返す。
- ICMP は知らせるだけで、再送はしない。再送が必要なら TCP やアプリが受け持つ。

**ICMP はどの層のプロトコルか**

- ICMP のメッセージは IP パケットのペイロードに入れて運ばれる。ただし TCP や UDP の上ではなく、IP と同じネットワーク層の一部として扱われる。
- ポート番号は持たない。アプリ同士の通信ではなく、ホストやルーターの間で IP の状態をやり取りするためのものだから。

**ICMP のタイプ**

ICMP のメッセージは、先頭の「タイプ」という番号で種類を見分ける。さらに「コード」という番号で、同じタイプの中の詳しい理由を表す。

| タイプ | メッセージ | 送る側 | 意味 | 使われる場面 |
| --- | --- | --- | --- | --- |
| 0 | エコー応答 | 相手のホスト | 「届いています」 | `ping` の返事 |
| 3 | 宛先到達不能 | ルーター / 宛先のホスト | 宛先のネットワークやホスト、ポートに届けられなかった | 宛先への経路がない、宛先のポートでアプリが待ち受けていない |
| 5 | リダイレクト | ルーター | 「その宛先なら、別のルーターに渡したほうが近い」 | 同じネットワークに複数のルーターがあるとき |
| 8 | エコー要求 | 確かめたいホスト | 「届きますか？」 | `ping` で相手につながるか確かめる |
| 11 | 時間超過 | ルーター | パケットの寿命（TTL）が尽きたので捨てた | `traceroute`（Windows では `tracert`）で経路上のルーターを調べる |
| 12 | パラメーター問題 | ルーター / 宛先のホスト | IP ヘッダーの中身がおかしいので捨てた | ヘッダーの値が不正なとき |

- タイプ 4（送信元抑制）や、タイプ 13・14（タイムスタンプ要求・応答）のように、決められてはいるが今はほとんど使われないタイプもある。

**タイプ 3（宛先到達不能）の主なコード**

| コード | 意味 |
| --- | --- |
| 0 | ネットワーク到達不能（宛先のネットワークへの経路がない） |
| 1 | ホスト到達不能（宛先のネットワークには着いたが、ホストが応答しない） |
| 3 | ポート到達不能（ホストには着いたが、そのポートで待ち受けているアプリがない） |
| 4 | 分割が必要だが、分割禁止が指定されている（パケットが大きすぎて通れない） |
| 13 | 管理上の理由で通信が禁止されている（ファイアウォールなどで止められた） |

**タイプ 11（時間超過）のコード**

| コード | 意味 |
| --- | --- |
| 0 | 転送中に TTL が 0 になった |
| 1 | 分割されたパケットを組み立て直す途中で、時間切れになった |

**ping と traceroute のしくみ**

- `ping` はエコー要求（タイプ 8）を送り、エコー応答（タイプ 0）が返ってくるかと、返ってくるまでの時間を表示する。
- `traceroute` は TTL を 1、2、3… と増やしながらパケットを送る。TTL はルーターを1つ通るたびに1減り、0 になったルーターが時間超過（タイプ 11）を返す。返してきたルーターを順に並べると、宛先までの経路が分かる。
- Windows の `tracert` はエコー要求を送るので、宛先に着くとエコー応答が返る。Linux の `traceroute` は初期設定では UDP のパケットを使われていなさそうなポートに送るので、宛先に着くとポート到達不能（タイプ 3・コード 3）が返る。どちらも、その返事で宛先に着いたと分かる。

**注意: ICMP をすべて止めると困ることがある**

- 攻撃の下調べに `ping` が使われるのを防ぐため、ファイアウォールでエコー要求を止めることがある。そのため、`ping` が返ってこなくても相手が止まっているとは限らない。
- ICMP をすべて止めると、「パケットが大きすぎて通れない」という知らせ（タイプ 3・コード 4）も届かなくなる。送信元はパケットを小さくすべきだと気づけず、大きなデータだけ通信できなくなることがある。
- IPv6 では ICMPv6 が使われ、同じネットワーク内の相手の MAC アドレスを調べる役割（IPv4 の ARP にあたる）も担う。そのため IPv6 では ICMPv6 を止めると通信そのものができなくなる。

**ICMPv6 のタイプ**

ICMPv6 は IPv4 の ICMP と番号の振り方が違う。1〜127 がエラーの知らせ、128〜255 が情報のやり取りに使われる。

| タイプ | メッセージ | IPv4 の ICMP でいうと |
| --- | --- | --- |
| 1 | 宛先到達不能 | タイプ 3 |
| 2 | パケット過大（パケットが大きすぎて通れない） | タイプ 3・コード 4 |
| 3 | 時間超過 | タイプ 11 |
| 4 | パラメーター問題 | タイプ 12 |
| 128 | エコー要求 | タイプ 8 |
| 129 | エコー応答 | タイプ 0 |
| 135 | 近隣要請（相手の MAC アドレスを尋ねる） | ARP の要求 |
| 136 | 近隣広告（自分の MAC アドレスを答える） | ARP の応答 |

参考: https://www.rfc-editor.org/rfc/rfc792

参考: https://www.rfc-editor.org/rfc/rfc4443

参考: https://www.iana.org/assignments/icmp-parameters/icmp-parameters.xhtml
:::
