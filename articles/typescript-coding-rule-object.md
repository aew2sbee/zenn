## 🌱 はじめに

この記事では、TypeScript で**オブジェクト指向らしい設計にする方法**を解説します。
下記の書籍（増田亨『現場で役立つシステム設計の原則』）で紹介されている、オブジェクト指向らしい設計のための 9 つのルールを要約したものです。9 つのルールの原典は、『ThoughtWorksアンソロジー』に収録されている「オブジェクト指向エクササイズ」です。
コード例は、筆者が TypeScript で作成したものです。

:::details 参考資料
@[card](https://gihyo.jp/book/2017/978-4-7741-9087-7)
:::

## 🌱 1. 1 つのメソッドのインデントは 1 つまで

1 番深いインデントの処理をメソッドに抽出し、次に深いインデントの処理もさらにメソッドに抽出していきます。
インデントは 1 つの処理単位なので、その単位をメソッドやクラスに抽出して部品化します。

## 🌱 2. else 句を使わない

else 句を使うと if 文が複雑になり、読みにくく、変更にも対応しにくくなります。
ガード節と早期リターンを組み込み、else 句を回避します。

```ts
function calculateDiscount(price: number): number {
  // ガード節で入力値をチェックし、条件を満たさない場合は先に処理を抜ける
  if (price <= 0) {
    throw new Error("価格は正の値でなければなりません");
  }

  // ガード節を通過した場合の処理
  const discount: number = price * 0.1;
  const discountedPrice: number = price - discount;
  return discountedPrice;
}
```

## 🌱 3. すべてのプリミティブ型と文字列をラップする

数値や文字列を「判断」「加工」「計算」するロジックを、そのデータを持つクラスに置くことで、コードの重複が減り、変更の影響範囲を 1 つのクラスに閉じ込めることができます。

プリミティブ型と文字列を引数として渡したり、メソッドの戻り値として使ったりすると、
ロジックがどこに書いてあるか分かりにくくなります。
※ TypeScript では文字列（`string`）もプリミティブ型ですが、原典が Java の文脈のため、文字列を別に挙げています。

ロジックと、そのロジックが使うプリミティブ型や文字列のデータを、いつも同じクラスにまとめておきます。

:::details [Q] プリミティブ型とは?
[A] プログラミング言語において基本的なデータ型のことです。TypeScript では、`number`、`string`、`boolean`、`bigint`、`symbol`、`null`、`undefined`がプリミティブ型です。
:::

## 🌱 4. 1 行につきドットは 1 つまで

ドットを使った複数のメソッドを連ねた文は、意図が分かりにくくなります。
同じ処理があちこちに重複して書かれる原因にもなります。

このルールを実践する方法は、**ドットの 1 つごとに説明用の変数に代入して別の文に分けることです。**
説明用の変数名で意図を明確にします。

1 つひとつの処理を独立させれば、メソッドやクラスに抽出しやすくなり、コードの再利用の機会も増えます。

:::message alert
ドットが複数ある**良くないコード**

```ts
const result = object.method1().method2().method3();
```

:::

ドットの 1 つごとに、説明用の変数に代入したコード

```ts
const order = customer.latestOrder();
const items = order.items();
const total = items.totalPrice();
```

:::message
このルールの本来の狙いは、オブジェクトの内部構造を外からたどらないこと（デメテルの法則）です。変数に分けても、内部構造をたどっている点は変わりません。`customer.latestOrderTotalPrice()`のように、データを持つクラスに処理を依頼する形にできないかも検討します。
なお、`array.filter().map()`のように、同じ種類のオブジェクトを返すメソッドチェーンは、このルールの対象外と考えてよいです。
:::

## 🌱 5. 名前を省略しない

オブジェクト指向は、利用者の関心事とソフトウェアのプログラム単位とを直接的に関連付ける技法です。

そのため、「クラス名」「関数名」「変数名」が利用者の関心事と一致していることが大事です。略語ではなく、辞書に載っている単語を使用します。

## 🌱 6. すべてのエンティティを小さくする

データを持つクラスにロジックを移動し、そのクラスに処理を依頼するため、そのクラスを使う側のコードがシンプルになります。

インスタンス変数とメソッドの結びつきごとにグルーピングしてクラスを抽出すれば、クラスは必然的に小さくなります。

クラスが増えたら、パッケージ（TypeScript ではモジュールやディレクトリ）でグルーピングします。
長いメソッド、巨大なクラス、クラスの数が多いパッケージは、設計がうまくいっていない兆候です。

| 対象                   | ガイドライン                         |
| ---------------------- | ------------------------------------ |
| メソッドの行数         | 3 行を目標にする。1 行でもよい       |
| クラスの行数           | 50 行を目標にする。100 行以上は不可  |
| パッケージのファイル数 | 10 ファイル以内                      |

## 🌱 7. 1 つのクラスのインスタンス変数は 2 つまで

インスタンス変数とメソッドの関連付けを徹底するためのルールです。

インスタンス変数とメソッドが密接に結び付いたクラスは、
目的が単純で意図が明確です。

どこに何が書いてあるのかの特定がしやすく、変更の箇所とその影響範囲をクラスに閉じ込めやすいです。

インスタンス変数が増えると、クラスの意図がだんだんぼやけてきます。

## 🌱 8. ファーストクラスコレクションを使う

関連するデータとロジックをできるだけ近くに置くのが鉄則です。

配列やコレクションの操作は、コードが複雑になりやすく、バグが混入しやすい場所です。
そのため、対象の配列/コレクションを 1 つだけインスタンス変数に持つ独立したクラスを作り、操作するロジックをそのクラスに集めて管理します。

## 🌱 9. 「getter」「setter」「プロパティ」を使わない

「getter」「setter」「プロパティ」は、データクラスで使われる書き方です。

メソッドは、何らかの「判断」「加工」「計算」をするべきです。
インスタンス変数をそのまま返すだけの「getter」は使いません。
「setter」は、プログラムの挙動を不安定にし、バグの原因になります。
