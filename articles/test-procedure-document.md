## 🌱 はじめに

2026年8月27日に発売された『QAエンジニア入門 〜チームで品質を高める連携のしかた』（岩崎 駿 著）を読みました。
テスト手順書の書き方について、誰にも教わることがなく「自分だけ分かればいいや」という手順書を作成しておりました。
改めて学び直すため、備忘録として残します。

https://gihyo.jp/book/2026/978-4-297-15832-3

「自分だけ分かればいいや」で書いた手順書は、次のような困り方をします。

- 3か月後の自分が読んでも、どのアカウントで試したのか分からない
- レビュー時に「その手順で本当に不具合が再現するのか」を追えない
- 他の人に実施を代わってもらえない

## 🌱 結論

:::message alert
※AIでの開発を前提に、自分なりにアレンジした構成となっております。
一意見として参考にしてみてください。
:::

:::message
**ディレクトリ構成**
```text
docs/
└── テスト/
    └── YYYY-MM-DD_Issue名/
        ├── テスト観点表.tsv
        └── テスト手順書.md
```

**テスト観点表.tsv**
※ 一般的には、Excelやスプレッドシートで表を作成するプロジェクトが多いと思いますが、
今回はAIが操作しやすくGitHubで管理ができる、軽量なTSV形式を選択しました。

**テスト手順書.md**
Excelやスプレッドシートなどの表に箇条書きの手順は書きにくいし、個人的には閲覧しにくいため、
手順書だけはmdファイルで管理しようと思います。

:::

Issueごとにフォルダを切ると、次のようになります。

```text
docs/
└── テスト/
    ├── 2026-09-10_購入フロー改修/
    │   ├── テスト観点表.tsv
    │   └── テスト手順書.md
    └── 2026-09-14_カート集計バグ修正/
        ├── テスト観点表.tsv
        └── テスト手順書.md
```

フォルダ名を `YYYY-MM-DD_Issue名` にしているのは、次の2点が理由です。

- 日付を先頭に置くと、名前順に並べたときに時系列になる（日付はIssueの着手日にしています）
- Issue単位でフォルダを切ると、「この改修で何をテストしたか」が1か所にまとまる

:::message
以降の例に出てくるURL・アカウント・パスワード・ブラウザのバージョンなどは、説明用の架空の値です。
:::

## 🌱 なぜ2つのファイルに分けるのか

観点表と手順書は、書く目的が違います。

| ファイル | 役割 | 読むタイミング |
| ---- | ---- | ---- |
| テスト観点表.tsv | 何をテストするかの一覧。抜け漏れを探す | 設計レビュー時・実施前 |
| テスト手順書.md | どう操作するかの詳細。同じ結果を再現する | 実施時・不具合の報告時 |

1つのファイルにまとめると、「一覧として眺めたいのに1行が長すぎる」状態になります。
観点表は一覧性、手順書は具体性と割り切って書こうと思います。

## 🌱 テスト観点表.tsv

次は `2026-09-10_購入フロー改修` の観点表です。1つのIssueで触る範囲を、1枚に並べます。

| ID | 画面 | 対象 | 目的・観点 | 前提条件 | 手段 | 期待結果 |
|---|---|---|---|---|---|---|
| TC-001 | ログイン画面 | ログインフォーム | 正しいメールアドレスとパスワードでログインできること（仕様どおりの動作） | 有効な会員アカウントが登録済みで、未ログイン状態であること | テスト手順書.md参照 | マイページへ遷移し、ヘッダーに登録名が表示される |
| TC-002 | 商品詳細画面 | 数量入力欄 | 在庫数5の商品に6を入力した場合に適切にエラー処理されること（入力値の処理／境界値） | 在庫数5の商品が公開されていること | テスト手順書.md参照 | カートに追加されず、「在庫数を超えています」のエラーメッセージが表示される |
| TC-003 | カート画面 | 購入確定ボタン | 1秒以内に3回クリックしても注文が二重登録されないこと（データ整合性） | カートに商品1点が入っており、決済情報が登録済みであること | テスト手順書.md参照 | 注文完了画面へ遷移し、注文履歴に登録される注文は1件のみである |
| TC-004 | マイページ | ログインセッション | 再読み込みしてもログイン状態が維持されること（仕様どおりの動作） | TC-001 を実施し、ログイン済みであること | テスト手順書.md参照 | ログイン画面に戻らず、マイページの表示が維持される |
| TC-005 | マイページ | URLの直接アクセス | 未ログイン状態ではマイページを閲覧できないこと（権限・認可） | 未ログイン状態であること | テスト手順書.md参照 | ログイン画面へリダイレクトされ、マイページの内容が表示されない |

### 各列の役割

| 列 | 書くこと | 書かないこと |
| ---- | ---- | ---- |
| ID | `TC-001` のような固定の番号。不具合報告や手順書から参照する | 行の並び替えで変わる連番 |
| 画面 | テスト対象の画面名 | 画面遷移の説明 |
| 対象 | 画面の中のどの要素か（フォーム・ボタン・入力欄） | 内部の実装名 |
| 目的・観点 | 何を確かめたいか。カッコ内に観点の分類を添える | 操作の手順 |
| 前提条件 | このテストを始められる状態 | 手順の1歩目 |
| 手段 | 実施方法。詳細は手順書へ委ねる | 手順そのもの |
| 期待結果 | 観点に対する答えを1〜2文で | 画面ごとの細かい表示崩れ |

観点表に書いていない期待結果を、手順書だけに足さないのも決めごとにしています。
手順書にしかない確認は、観点表をレビューしたときに見つけられません。

### TSVの実体

Markdownの表として貼っていますが、ファイルの中身はタブ区切りのテキストです。
1行目のヘッダーと TC-001 を抜粋すると、次のようになります。

```text:テスト観点表.tsv
ID	画面	対象	目的・観点	前提条件	手段	期待結果
TC-001	ログイン画面	ログインフォーム	正しいメールアドレスとパスワードでログインできること（仕様どおりの動作）	有効な会員アカウントが登録済みで、未ログイン状態であること	テスト手順書.md参照	マイページへ遷移し、ヘッダーに登録名が表示される
```

CSVではなくTSVにしているのは、金額を読みやすくするために「,」（例: 24,000）を使うことがあるためです。
CSVでも引用符で囲めば書けますが、そのぶん差分が読みにくくなるので、タブ区切りを選びました。

### 観点の分類を添える

`目的・観点` のカッコ内に分類を書いておくと、一覧を眺めたときに偏りが見えます。

```diff text:目的・観点の書き方
- ログインのテスト
+ 正しいメールアドレスとパスワードでログインできること（仕様どおりの動作）
```

私は、ひとまず次の4分類で書き分けています。

- 仕様どおりの動作（正常系）
- 入力値の処理／境界値
- データ整合性
- 権限・認可

「仕様どおりの動作」ばかり並んでいたら、異常系の観点が抜けていると思ってよさそうです。

## 🌱 テスト手順書.md

観点表の1行につき、手順書の1セクションが対応します。
TC-001 を例にすると、次の形になります。

```md:テスト手順書.md
# テスト手順書（2026-09-10_購入フロー改修）

## TC-001 ログイン画面 / ログインフォーム

### 1. 目的・観点

正しいメールアドレスとパスワードでログインできること（仕様どおりの動作）

### 2. 前提条件

- 環境: ステージング（`https://stg.example.com`）
- OS / ブラウザ: Windows 11 / Google Chrome 139.0.7258.67
- アカウント: `test.user01@example.com`（有効な会員アカウント、登録名「テスト太郎」）
- 状態: 未ログイン（シークレットウィンドウで実施）

### 3. テストデータ

| 項目 | 値 |
| ---- | ---- |
| メールアドレス | `test.user01@example.com` |
| パスワード | `Test@12345` |

### 4. テスト手順

1. `https://stg.example.com/login` にアクセスする。
2. メールアドレス欄に `test.user01@example.com` を入力する。
3. パスワード欄に `Test@12345` を入力する。
4. 「ログイン」ボタンを1回クリックする。

### 5. 期待結果

| No. | 手順 | 期待結果 |
| ---- | ---- | ---- |
| EXP-1 | 4 | マイページ（`/mypage`）へ遷移する |
| EXP-2 | 4 | ヘッダーに「テスト太郎」と表示される |

### 6. 実施結果

| 実施日 | 実施者 | 結果 | NG手順 | 備考 |
| ---- | ---- | ---- | ---- | ---- |
| 2026-09-13 | aew2sbee | NG | 4 | EXP-2: 登録名ではなくメールアドレスが表示された。Issue #123 で起票 |
| 2026-09-14 | aew2sbee | OK | - | #123 の修正後に再実施 |
```

観点表の `期待結果` は一覧で読める要約、手順書の `期待結果` は手順ごとの確認内容、
という粒度の違いを意識して書き分けています。

期待結果に `EXP-1` のようなIDを振っているのは、不具合報告などから期待結果を参照するときに、
手順を1つ足しただけで手順番号がずれて、参照が合わなくなるのを避けるためです（表の「手順」列は、手順を足したら直します）。

`実施結果` は `OK` / `NG` / `実施不可`（前提条件を用意できず実施できなかった場合）の3つで書きます。
これを手順書と同じファイルに置いているのは、
「どの手順で落ちたのか」をあとから追うときに、手順と結果が離れていると照合しづらいためです。

### 繰り返す操作をどう書くか

TC-003 の「1秒以内に3回クリック」のように、繰り返しそのものが観点になることがあります。
この場合は手順を3行に分けず、回数と間隔を書いた1手順にします。

```md:テスト手順書.md（TC-003 抜粋）
## TC-003 カート画面 / 購入確定ボタン

### 4. テスト手順

1. `https://stg.example.com/cart` にアクセスする。
2. 「購入を確定する」ボタンを1秒以内に3回クリックする。

### 5. 期待結果

| No. | 手順 | 期待結果 |
| ---- | ---- | ---- |
| EXP-1 | 2 | 注文完了画面（`/orders/complete`）へ遷移する |
| EXP-2 | 2 | 注文履歴に登録される注文は1件のみである |
```

## 🌱 手順を書くときのコツ

### 1手順に1操作だけ書く

```diff text:手順の粒度
- 1. ログイン画面でメールアドレスとパスワードを入力してログインする
+ 1. メールアドレス欄に `test.user01@example.com` を入力する
+ 2. パスワード欄に `Test@12345` を入力する
+ 3. 「ログイン」ボタンを1回クリックする
```

1手順に複数の操作をまとめると、失敗したときにどこで落ちたのか特定できません。
不具合報告に「手順3まで成功、手順4で発生」と書けるかを基準にしています。

### 値をぼかさない

```diff text:テストデータの書き方
- 2. 在庫数を超える数量を入力する
+ 2. 数量入力欄に `6` を入力する（商品の在庫数は5）
```

「超える数量」では、具体的な値を読み手が決めることになり、実施する人によって入力値が変わります。
在庫5の商品に `6` を入れたのか `100` を入れたのかで、見ている境界が変わります。

### 判断を手順に混ぜない

```diff text:手順と期待結果の分離
- 5. 遷移後の画面を確認する
- 6. ヘッダーの表示を確認する
+ 4. 「ログイン」ボタンを1回クリックする
+    （画面の確認内容は「5. 期待結果」に記載）
```

手順に「〜を確認する」と書くと、合格の基準が手順書の中に散らばります。
操作は手順、合否の判断は期待結果、と置き場所を固定します。
手順に並ぶのは操作だけなので、最後の操作で手順は終わりです。

### 画面の表記をそのまま書く

```diff text:要素の指定
- 4. 送信ボタンを押す
+ 4. 「ログイン」ボタンを1回クリックする
```

画面に「ログイン」と書いてあるボタンを「送信ボタン」と呼ぶと、実施者がボタンを探すところから始まります。
UIのラベルはカギカッコで囲って、画面の表記をそのまま引用します。

### 前提条件に環境とアカウントを必ず書く

```diff text:前提条件の書き方
- 前提: ログインできる状態であること
+ 前提:
+ - 環境: ステージング（`https://stg.example.com`）
+ - OS / ブラウザ: Windows 11 / Google Chrome 139.0.7258.67
+ - アカウント: `test.user01@example.com`（有効な会員アカウント）
+ - 状態: 未ログイン（シークレットウィンドウで実施）
```

再現しない不具合の原因は、手順ではなく前提条件の違いであることが多いです。
「ブラウザは最新版」のような書き方だと、3か月後に同じ環境を作れないので、バージョンまで書きます。
環境・アカウント・データの3つは、毎回書くと決めてしまおうと思います。

## 🌱 AIに渡す前提で書く

この構成にしている一番の理由は、そのままAIに渡せるようにするためです。

**観点表を渡して手順書を書かせる**

観点表の1行と画面のUI情報を渡すと、手順書の下書きが作れます。
このとき、前述の「1手順に1操作」「値をぼかさない」が効いてくるはずです。
曖昧な表現が残っていると、AIが手順を勝手に補完して、実際の画面と合わない手順書ができあがります。

**手順書を渡して実施させる**

ブラウザ操作ができるAIに手順書を渡す場合も、書き方は人間向けのままで通用するのではないかと思っています。
「ボタンを押す」ではなく「『ログイン』ボタンを1回クリックする」と書いてあれば、そのまま実行できるはずです。
※ こちらはまだ試せていないので、実際に動かしたら別記事にまとめます。

:::message alert
AIに実施させる場合は、対象環境を必ずステージングなどの検証用環境に限定してください。
本番環境の手順書をそのまま渡すと、本当に注文が確定します。
:::

**差分をレビューする**

TSVとMarkdownにしておくと、観点や手順の変更がPull Requestの差分として残ります。
「どの観点を追加したのか」がレビューできるのは、Excel管理にはない利点だと思います。

## 🌱 おわりに

テスト手順書を書き直してみて、一番変わったのは
`手順` と `期待結果` を分けて書くようになった点です。

以前は「ログインできることを確認する」の1行で済ませていましたが、
これでは、何を操作して何が起きれば合格なのかが自分の頭の中にしかありませんでした。

私はまず、次の3つから始めようと思います。

- 前提条件に、環境・アカウント・データを書く
- 1手順に1操作だけ書く
- 入力値を具体的な値で書く

この3つだけでも、「3か月後の自分が読んで再現できる手順書」に近づけると思っています。
