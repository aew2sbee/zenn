## 🌱 はじめに

約 2 年間 QA エンジニアとして活動しておりました。
社内メンバーにテストに関する初歩の知識を共有したく執筆します。

考えた方がいいテスト観点を並べるだけでは、理解が難しいと考えたため
サンプルの仕様を例にしてテストパターンを考えたいと思います。

## 🌱 仕様

`年齢`と`性別`の入力欄に値を入力すると
DB から`料金`の値を返してくれる機能があるとします。

![test-image](/images/articles/thinking-test-pattern/test-image.png)

詳細の仕様は下記のとおりです。

| 利用する人               | 料金     |
| ------------------------ | -------- |
| `0`~`6`歳未満の子供      | `0`円    |
| `6`~`18`歳未満の`女の子` | `450`円  |
| `6`~`18`歳未満の`男の子` | `500`円  |
| `18`歳以上の`女性`       | `1000`円 |
| `18`歳以上の`男性`       | `1200`円 |

例えば、`10`歳の`男の子`なら料金は`500`円になります。

データでイメージするなら、`Input.json`が利用する人の入力データです。
料金のデータを`Output.json`で表現します。

```json:Input.json
{
    "age" : 10,
    "gender" : "male"
}
```

```json:Output.json
{
    "price" : 500
}
```

いきなり、テストのパターンを考えるのは難しいので、スコープを小さくして考えます。

## 🌱 Q. 年齢に関して何パターンを想定したら良いのか

### 1. まずは、仕様から読み取れるテストパターンを算出する

年齢に関する仕様を表形式にまとめると下記のとおりになります。
`0 <= age < 6`, `6 <= age < 18`, `18 <= age`の最低でも**3 パターン**のテストが必要そうですね。

| 項目     | 内容            |
| -------- | --------------- |
| **子供** | `0 <= age < 6`  |
| **学生** | `6 <= age < 18` |
| **成人** | `18 <= age`     |

しかし、これだけではテストパターンは不十分です。
`境界値分析`と`同値分割法`の観点でテストパターンを追加できるか確認しましょう。

#### 「境界値分析」とは

境界値分析とは、ブラックボックステスト技法の一つであり、境界となる値（同値クラスの端）とその前後の値に対してテストする技法です。

#### 「同値分割法」とは

同値分割法とは、ブラックボックステスト技法の一つであり、入力値を同じ処理をするグループに分割し、グループ内で代表的な入力値を選択してテストする技法です。

### 2. 境界値分析（境界となる値）を考慮したら

境界となる値は、料金が切り替わる`6`,`18`と、入力できる範囲の下限である`0`の 3 つです。
※仕様に年齢の上限がないため、上限（例: `150`歳のような極端に大きな値）をどう扱うかは、仕様の確認が必要です。

### 3. 境界値分析（境界値の前後の値）を考慮したら

- 境界値`0`に対して「`-1`,`1`」が考えられる
- 境界値`6`に対して「`5`,`7`」が考えられる
- 境界値`18`に対して「`17`,`19`」が考えられる

### 4. 境界値分析を考慮した結果をまとめると

年齢に対する「`-1`,`0`,`1`,`5`,`6`,`7`,`17`,`18`,`19`」の**9 パターン**が想定できます。
`-1`は、仕様の範囲外（年齢として入力できない値）のため、エラーになることを確認します。

### 5. 同値分割法を考慮したら

※代表的な入力値は、グループの範囲内であればどの値でも大丈夫です。
範囲の**中央付近の値**を選ぶと考えやすいです。

- `age < 0`（仕様の範囲外）に対して「`-3`」が考えられる
- `0 <= age < 6`に対して「`3`」が考えられる
- `6 <= age < 18`に対して「`9`」が考えられる
- `18 <= age`に対して「`21`」が考えられる

### 6. 境界値分析と同値分割法を考慮した結果をまとめると

年齢に対する「`-3`,`-1`,`0`,`1`,`3`,`5`,`6`,`7`,`9`,`17`,`18`,`19`,`21`」の**13 パターン**が想定できます。
:::message
Q. 年齢に関して何パターンを想定したら良いのか？
A. 年齢に対して**13 パターン**
:::

## 🌱 Q. 性別に関して何パターンを想定したら良いのか

### 1. まずは、仕様から読み取れるテストパターンを算出する

`男性`, `女性`の**2 パターン**はテストパターンが必要そうですね。

しかし、これだけではテストパターンは不十分です。
同様に`同値分割法`の観点でテストパターンを追加できるか確認しましょう（性別には数値のような大小がないため、境界値分析は使いません）。

### 2. 同値分割法を考慮したら

仕様にない値のグループとして、`男性`, `女性`以外の`その他`が想定できます。

### 3. 同値分割法を考慮した結果をまとめると

性別に対する`男性`,`女性`,`その他`の**3 パターン**が想定できます。
:::message
Q. 性別に関して何パターンを想定したら良いのか？
A. 性別に対して**3 パターン**
:::

## 🌱 Q. 年齢と性別の組み合わせで想定されるテストパターンとは

これらを組み合わせると、年齢に対する**13 パターン**と性別に対する**3 パターン**の組み合わせで、**39 パターン**が想定できます。
仕様の範囲外の値（年齢の`-3`,`-1`、性別の`その他`）を含む組み合わせは、エラーになることを確認します。
:::message
Q. 年齢と性別の組み合わせで想定されるテストパターンとは？
A. **39 パターン**(13*3=39)が想定できます
:::

| -3   | Error   | Error   | Error  |

| 0    | 0 円    | 0 円    | Error  |
| 1    | 0 円    | 0 円    | Error  |
| 3    | 0 円    | 0 円    | Error  |
| 5    | 0 円    | 0 円    | Error  |
| 6    | 450 円  | 500 円  | Error  |
| 7    | 450 円  | 500 円  | Error  |
| 9    | 450 円  | 500 円  | Error  |

## 🌱 Q. 【異常系】入力値の型が違うパターンも想定していますか

### 1. 数値ではなく文字列の場合

値が同じ`6`でも、型が違う場合に正しく動作するのか？

```diff json:Input.json
 {
-    "age" : 6,
+    "age" : "6",
    "gender" : "female"
 }
```

### 2. 整数ではなく小数の場合

同じ値を示す`6.0`でも正しく動作するのか？
※JSON では、`6`と`6.0`はどちらも数値として扱われます。受け取る側のプログラムが整数と小数を区別している場合に確認します。

```diff json:Input.json
 {
-    "age" : 6,
+    "age" : 6.0,
    "gender" : "female"
 }
```

#### データ型の一覧

| データ型                        | 説明                                                              | 例                               |
| ------------------------------- | ----------------------------------------------------------------- | -------------------------------- |
| **整数（int 型）**              | 小数を含まない値を扱うためのデータ型。                            | 0、1、100、999、-123             |
| **小数（float 型、double 型）** | 小数を含む値を扱うためのデータ型。                                | 1.23、3.14、-99.9                |
| **文字列（String 型）**         | 文字列を扱うためのデータ型。ダブルクオーテーション(")でくくります。 | "ABC"、"TOKYO"、"プログラミング" |
| **論理型（boolean 型）**        | 「真」「偽」を扱うためのデータ型。                                | true、false                      |
| **日付型（datetime 型）**       | 「日付」や「時間」を扱うためのデータ型。                          | 2024-01-01、2024-01-01 12:30:00  |
| **null 型**                     | 「値が存在しないこと」を扱うためのデータ型。                      | null                             |

:::message
すべての型のテストを実施すれば、より安全なプログラムになりますが、
すべてを実施するには時間が足りません。
なので、仕様に合わせて必要な型のみを実施することをおすすめします。
:::

## 🌱 Q. 【異常系】Key 名が間違っているパターンも想定していますか

プログラムの処理内で`"age"`という Key を探す処理があると思いますが、Key が見つからない場合に、想定外のエラーで処理が止まらないか？

```diff json:Input.json
 {
-    "age" : 6,
+    "agee" : 6,
    "gender" : "female"
 }
```

## 🌱 Q. 【異常系】余分な Key が追加されているパターンも想定していますか

入力データに`"name"`という余分な Key があった場合でも、期待どおりの`Output.json`が返ってくるか？

```diff json:Input.json
 {
    "age" : 6,
-    "gender" : "female"
+    "gender" : "female",
+    "name" : "taro"
 }
```

## 🌱 Q. 【異常系】必要な Key が不足しているパターンも想定していますか

`"age"`という Key がない場合に、想定外のエラーで処理が止まらないか？

```diff json:Input.json
 {
-    "age" : 6,
    "gender" : "female"
 }
```

## 🌱 Q. 【異常系】もし DB から返る値がないパターンも想定していますか

DB に必ずしもデータがあるとは限りません。
データがない場合でもシステムが異常終了せず、適切なエラー（エラーメッセージやエラーレスポンス）を返す対策が必要です。
例えば、「DB から取得した値が 0 件かどうか確認する処理」を追加するのも対策の 1 つです。

## 🌱 Q. 【異常系】もし DB にアクセスする途中で通信エラーが発生するパターンも想定していますか

DB にデータがあり、検索条件のデータも正しくても、何かしらの理由で DB にアクセスできない場合があります。
その場合にも対策が必要です。
例えば、「アクセスできなかったら、代わりにエラーメッセージを表示する」「少し時間を空けてもう一度 DB にアクセスする」などがあります。

## 🌱 Q. 【異常系】`gender`の値が異なるパターンも想定していますか

`"man"`は仕様にない値のため、プログラム上は`"その他"`と同じ扱い（エラー）になりますが、入力した人は男性のつもりです。
`male`と`man`は、どちらも`男`で同じ意味を持ちます。
つまり、担当するプログラマーが仕様を間違えるとエラーの原因になります。

```diff json:Input.json
 {
    "age" : 6,
-    "gender" : "male"
+    "gender" : "man"
 }
```

対策としては、「データを定数化し、メンバー内で認識を合わせて定数を使い回す」ことが挙げられます。

## 🌱 おわりに

今回はサンプルの仕様についてテストパターンを考えてみましたが、
サンプルの仕様に関連する機能がある場合は、条件が増えるためさらにテストパターンが増えます。
テストは、一見簡単そうな工程と思われますが、責任の重い大事な工程です。
