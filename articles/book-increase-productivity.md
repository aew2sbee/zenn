## 🌱 はじめに

牛尾剛『世界一流エンジニアの思考法』（文藝春秋、2023年）を読み、エンジニアの**生産性を上げる行動**として実践したいと思った5つをまとめます。

@[card](https://books.bunshun.jp/ud/book/num/9784163917689)

1. むやみに手を動かさない
2. 基礎ほど時間をかけて習得する
3. コードを書く前に小さなドキュメントを作成する
4. 全体を俯瞰的に把握する
5. やることを減らす

## 🌱 1. むやみに手を動かさない

「なんとなくここが問題じゃない？」と、闇雲に調査・検証を始めるのではなく、先に考えます。

1. 事実を1つ見つける
2. いくつかの仮説を立てる
3. その仮説を証明するために行動する

```diff
- 「なんとなくここが問題じゃない？」で闇雲に調査・検証を行う
- 【ポイント】調査・検証は時間のコストが大きい
+ 【ポイント】調査・検証より、先に考えるほうが時間のコストを抑えられる
```

## 🌱 2. 基礎ほど時間をかけて習得する

基礎を理解するには、誰でも時間がかかります。時間をかけてでも、基礎を身につけることが大切です。

```diff
- 「自分は飲み込みが悪いから…」→ 誰でも理解するには時間がかかる！
+ 就業後や週末に「プログラミングの基本」を学習する
+ その構造をつかみ、他人に説明できるようにする
+ いつでもどこでも、すぐに取り出して使えるようにする
+ 知見を踏まえて応用が利くようにする
+ 【ポイント】毎回ググっていると覚えられず、またググって時間がかかる
```

## 🌱 3. コードを書く前に小さなドキュメントを作成する

最初から網羅的な設計書を作るのではなく、コードを書く前に小さなドキュメントで要点を固めます。

```diff
- 何十ページにもなるドキュメントの作成は時間の無駄
+ 頭の中が整理され、考慮漏れを防げる
+ すでにできているので、退屈なドキュメントの整理をしなくてよい
```

ドキュメント全体の分量は、2〜10ページ程度が目安です。

:::message
**ドキュメントのテンプレート**

- **Scope**
  - このドキュメントの範囲を書く
- **Background**
  - なぜこの変更や開発を行うのか、その背景を書く
- **Problem Statement**
  - 解決したい問題を書く
- **Proposal**
  - どのような設計にするか、またその案を選んだ理由を論理的に書く

:::

## 🌱 4. 全体を俯瞰的に把握する

担当する部分だけでなく、システム全体を把握しておくと、次のような違いが生まれます。

```diff
- 不具合の特定に時間がかかる
- 改修や新規開発に時間がかかる
+ 不具合の特定を効率化できる
+ 改修や新規開発を効率化できる
```

## 🌱 5. やることを減らす

本書では、ソフトウェアの機能のうち、実際に使われるのは**40%程度**にとどまるという統計が紹介されています。
すべてをやろうとせず、やることを減らすことが大切です。

1. やることを**1つ**だけピックアップする
2. **時間を固定**して、できることを最大化する → 複数の課題があっても重要なものだけ！
3. **「準備」**や**「持ち帰り」**をやめて、その場で判断する
4. 物理的にやることを減らす → **できないものは素直に諦める**

## 🌱 まとめ

- むやみに手を動かさず、事実から仮説を立ててから検証する
- 基礎は時間をかけて、他人に説明できるまで習得する
- コードを書く前に、小さなドキュメントで要点を固める
- 全体を俯瞰して把握し、不具合の特定や改修を効率化する
- やることを1つに絞り、その場で判断して、やることを減らす
