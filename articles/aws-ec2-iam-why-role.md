## 🌱 はじめに

社内の有志メンバーでの活動で、上司に「スイッチロールできるように設定してください」と言われました。
タスク自体は完了しましたが、「なぜスイッチロールが必要なのか？」が分からないままでした。
そこで、自分なりに調べて考えた内容を執筆します。

### 対象読者

- AWS を触り始めたばかりの方
- スイッチロールを設定したことはあるが、必要な理由が分からない方

### この記事で分かること

- スイッチロールの仕組み
- スイッチロールを使うメリット

## 🌱 スイッチロールとは

スイッチロール（AWS の正式名称は「ロールの切り替え / Switch role」）は、IAM ユーザーでサインインしたまま、別の IAM ロールの権限に一時的に切り替える操作です。
内部では AssumeRole という仕組みで動いています。

まず、登場する用語を整理します。

| 用語 | 説明 |
| --- | --- |
| IAM ユーザー | AWS を操作する人ごとのアカウント |
| ポリシー | 「何を許可するか」を JSON 形式で書いた文書 |
| IAM ロール | ポリシーをまとめたもの。決められたユーザーだけが一時的に引き受けて（切り替えて）使える |

:::message
スイッチロール中は、元のユーザーの権限ではなく**ロールの権限だけ**で操作します。ユーザーの権限にロールの権限が上乗せされるわけではありません。
:::

## 🌱 スイッチロールのメリット

:::message

1. 必要な権限を簡単に付与・使い回しできる
2. 誤操作を防げる
3. 誰が操作したのかをログで確認できる

:::

## 🌱 1. 必要な権限を簡単に付与・使い回しできる

ここでは、**ReadOnlyAccess 権限のユーザーに EC2 の更新権限を付与したい場合**を例に考えます。

- ReadOnlyAccess: AWS が用意している、全サービスを読み取り専用で使える AWS 管理ポリシー
- EC2: AWS の仮想サーバーのサービス

ReadOnlyAccess 権限のユーザーは、EC2 の情報を読み取ることはできますが、**EC2 の設定を更新する**ことはできません。

![ReadOnlyAccess権限のユーザーがEC2の設定を更新できない様子を表した図](/images/articles/aws-ec2-iam-why-role/AWS-IAM-role-step01.png)
*ReadOnlyAccess 権限のユーザーは EC2 の設定を更新できないイメージ図*

### スイッチロールしなかった場合

ユーザーに EC2 用のポリシー（例: AmazonEC2FullAccess）を直接追加でアタッチします。
IAM では、1人のユーザーに付けた複数のポリシーの許可が合算されるため、ReadOnlyAccess はそのまま残して構いません。

手順は簡単ですが、次のデメリットがあります。

:::message alert

- EC2 を更新する必要がないときも、更新権限が常に付いたままになる
- 権限が必要なユーザーが増えるたびに、ユーザーごとにポリシーを付け外しする必要がある
- 誰にどの権限を付けたのかの管理が複雑になる

:::

### スイッチロールした場合

![スイッチロールでEC2の権限を持つロールに切り替え、EC2を操作する様子を表した図](/images/articles/aws-ec2-iam-why-role/AWS-IAM-role-step02.png)
*スイッチロールで EC2 の権限を持つロールに切り替えて操作するイメージ図*

1. EC2 の権限を許可するロールを作成する
2. ロールの信頼ポリシーで、切り替えを許可するユーザー（またはアカウント）を指定する
3. 必要に応じて、ユーザー側にも `sts:AssumeRole` を許可するポリシーを付ける
4. 対象ユーザーに、アカウント ID とロール名を伝える
5. 対象ユーザーは、コンソール右上のメニューからロールを切り替える

:::message
次のメリットが考えられます。

- ユーザーごとにポリシーを付け外しする必要がなく、権限をロールにまとめて管理できる
- 別のユーザーにも同じ権限が必要になったら、信頼ポリシーでそのユーザーの切り替えを許可するだけでよい

:::

## 🌱 2. 誤操作を防げる

普段は読み取り権限だけのユーザーで作業し、EC2 の停止や削除など更新が必要なときだけロールに切り替えます。
**必要なときに必要な権限だけを使う**ので、誤って設定を変更してしまうリスクを下げられます。
この考え方を「最小権限の原則」と呼びます。

料理に例えると、包丁🔪を台所に出しっぱなしにするより、具材を切るときだけ出して、終わったらしまう方が怪我のリスクを減らせるのと同じだと考えます。

## 🌱 3. 誰が操作したのかをログで確認できる

AWS の操作は、ルートユーザー（AWS アカウント作成時のすべての権限を持つユーザー）によるものも含めて、CloudTrail というサービスに記録されます。
しかし、ルートユーザーや1つの IAM ユーザーを複数人で共有していると、ログには「そのユーザーが操作した」としか残りません。
そのため、**実際にメンバーの誰が操作したのかは分かりません。**

一方、メンバーごとに IAM ユーザーを発行し、そこからスイッチロールする運用にすると、CloudTrail の AssumeRole のイベントで「いつ、誰が、どのロールに切り替えたのか」を確認できます。
切り替えた後の操作も、ロールのセッション情報から元のユーザーをたどれます。

## 🌱 おわりに

最初は「わざわざロールを切り替えるのは手間が増えるだけ」と思っていました。
調べてみると、スイッチロールには次のメリットがあると分かりました。

- 権限をロールにまとめて、必要なユーザーに使い回せる
- 必要なときだけ強い権限を使うので、誤操作を防げる
- メンバーごとのユーザーから切り替えるので、誰が操作したのかを追える
