## 🌱 はじめに

2026年8月27日に発売された『QAエンジニア入門 〜チームで品質を高める連携のしかた』（岩崎 駿 著、技術評論社）を読みました。
第2章「2.2 テスト計画：目的と作成方法」の記述を参考に、テスト計画書のテンプレートとしてまとめます。

https://gihyo.jp/book/2026/978-4-297-15832-3

テスト計画をはじめて任されると、何をどこまで書けばよいのかが分かりません。
そのまま埋めれば形になるように、Markdown のテンプレートとして用意しました。

書くことを決めないままテストを始めると、次のような困り方をしがちです。

- 「それもテストしてほしい」と途中で範囲が広がり、終わりが見えなくなる
- 不具合が何件残っていたらリリースしてよいのか、誰も決められない
- テスト環境が止まったときに、待つのか別の作業に切り替えるのかで迷う

:::message
- 各項目の引用は、すべて本書からの抜粋です
- 記入例のプロダクト・仕様・担当者名・チャンネル名は、説明のために用意した架空のものです
:::

5つの章は、次の問いに答える構成になっています。

| 章 | 答える問い |
| ---- | ---- |
| 1. はじめに | 何のためのテストか |
| 2. テストの全体像 | どこを、どの観点でテストするか |
| 3. テストの進め方 | いつ、誰が、何を作るか |
| 4. テスト完了の基準 | どうなったら終わりか |
| 5. リスク管理 | うまくいかなかったらどうするか |

## 🌱 記入例の題材

ここからは、テンプレートの例に出てくる「新規会員登録フロー改善」を題材に、各項目の記入例を書いていきます。

| 項目 | 内容 |
| ---- | ---- |
| プロダクト | ShopNote（架空のECアプリ。iOS / Android / Web） |
| バージョン | Ver2.3 |
| 変更内容1 | 会員登録の入力項目を8項目から4項目（メールアドレス・パスワード・ニックネーム・生年月日）に減らす |
| 変更内容2 | 本人確認を、メール認証からSMS認証（6桁の認証コード）に変更する |
| 変更内容3 | Googleアカウントでの登録を追加する |
| リリース予定日 | 2026-11-10 |

## 🌱 1. はじめに

### 1.1 目的

> このテスト計画書が、どのプロダクトの、どの機能リリースに関するものであるのかを記述する

```md:記入例
## 1.1 目的
ShopNote Ver2.3 の「新規会員登録フロー改善」リリースについて、
テストの範囲・進め方・完了基準を関係者で合意するための文書です。
```

プロダクト名とバージョンまで書くのは、同じ機能を次のバージョンでまた改修することがあるためです。

```diff text:目的の書き方
- 会員登録のテスト
+ ShopNote Ver2.3 の「新規会員登録フロー改善」リリースのテスト
```

「会員登録のテスト」だけだと、半年後に見返したときにどのリリースの文書なのか分かりません。

### 1.2 背景

> なぜこのテストが必要なのか、ビジネス的な背景や目的を簡潔に記載

```md:記入例
## 1.2 背景
- 会員登録画面での離脱率が62%あり、入力項目の多さが原因と分析された
- メール認証の認証メールが迷惑メールフォルダに振り分けられ、登録を完了できないという問い合わせが月40件ある
- 本リリースで、登録完了率を38%から50%に上げることを目標にしている
```

背景には、数字を1つは入れるようにしています。
「登録完了率を上げたい」という背景が分かっていれば、テストでも「登録を最後まで迷わず終えられるか」を重く見る、という判断につながります。

ここが空欄だと、後述の「2.3 テストで重視する観点」を決める理由がなくなります。

## 🌱 2. テストの全体像

### 2.1 テスト対象範囲

> 品質を確認する機能やコンポーネントを具体的にリストアップ

```md:記入例
## 2.1 テスト対象範囲
| No. | 対象 | 内容 |
| ---- | ---- | ---- |
| 1 | 会員登録画面 | 4項目の入力と入力チェック |
| 2 | SMS認証画面 | 認証コードの送信・入力・再送信・有効期限 |
| 3 | Googleアカウント連携 | Googleアカウントでの新規登録、登録済みメールアドレスとの重複時の挙動 |
| 4 | 登録完了後の遷移 | マイページへの遷移、登録完了メールの送信 |
| 5 | 対象環境 | iOS 18 / Android 15 のアプリ、Web版（Google Chrome / Safari の最新版） |
```

画面名だけでなく、その画面の中で何を見るのかまで書きます。

```diff text:対象範囲の書き方
- SMS認証
+ SMS認証画面（認証コードの送信・入力・再送信・有効期限）
```

「SMS認証」とだけ書くと、再送信や有効期限切れまで含むのかが読み手によって変わります。

### 2.2 テスト対象外範囲

> 品質を確認しない機能やコンポーネントを具体的にリストアップ（追加要望対策のため）

```md:記入例
## 2.2 テスト対象外範囲
| No. | 対象 | 対象外とする理由 |
| ---- | ---- | ---- |
| 1 | メールアドレスでのログイン | 本リリースで変更がないため。既存の自動テストで確認する |
| 2 | Googleアカウント側の認証画面 | Google が提供する画面であり、ShopNote 側で制御できないため |
| 3 | SMSの到達率 | SMS送信サービス側の品質であるため。送信APIの呼び出しまでを対象とする |
| 4 | 商品一覧・商品詳細画面 | 会員登録と関係がなく、本リリースで変更がないため |
```

対象外範囲には、必ず理由を添えます。

理由がないと、「ログイン画面もついでに見ておいて」と言われたときに断る根拠がありません。
逆に、理由を書いておけば「変更がないから対象外にした」と説明でき、それでも必要だと判断されたら対象範囲に移せます。

:::message
対象外にした範囲で不具合が見つかったとき、なぜテストしなかったのかを説明する根拠になるのもこの項目です。
「判断して外した」と「気付かずに漏れた」を区別するために書きます。
:::

### 2.3 テストで重視する観点(テストタイプ)

> 機能テストに加え、ユーザビリティ、パフォーマンス、セキュリティなど、今回のリリースで特に重視する品質特性を定義

```md:記入例
## 2.3 テストで重視する観点(テストタイプ)
| 観点 | 重視度 | 理由 |
| ---- | ---- | ---- |
| 仕様どおりの動作 | 高 | 登録フローそのものを作り直すため |
| ユーザビリティ | 高 | 離脱率の改善が目的のため。エラーメッセージで次の操作が分かるかを見る |
| セキュリティ | 高 | 認証コードの総当たり、他人の電話番号での登録を防げるかを見る |
| データ整合性 | 中 | Googleアカウント連携で、既存会員と重複したときに会員データが二重に作られないかを見る |
| パフォーマンス | 低 | 画面の構成は変わらないため。外部API（SMS送信・Google認証）の応答待ちは、機能テストの中でタイムアウト時の挙動として確認する |
```

全部の観点を「高」にすると、優先度を決めたことになりません。
「1.2 背景」とつなげて、重視する理由を書ける観点だけを「高」にしています。

観点の一覧は、別の記事にまとめています。

@[card](https://zenn.dev/aew2sbee/articles/test-perspectives)

## 🌱 3. テストの進め方

### 3.1 スケジュール

> テスト計画、設計、実施、報告といった各フェーズの開始日と終了日をマイルストーンとして設定

```md:記入例
## 3.1 スケジュール
| フェーズ | 開始日 | 終了日 | マイルストーン |
| ---- | ---- | ---- | ---- |
| テスト計画 | 2026-10-01 | 2026-10-05 | 本書のレビュー完了 |
| テスト設計 | 2026-10-06 | 2026-10-16 | テスト観点表・テスト手順書のレビュー完了 |
| テスト実施 | 2026-10-19 | 2026-10-30 | テストケースの消化率100% |
| 再テスト | 2026-11-02 | 2026-11-05 | 修正した不具合の確認完了 |
| テスト報告 | 2026-11-06 | 2026-11-06 | テスト完了報告書の承認 |
```

テスト実施とは別に、再テストの期間を取っています。

テスト実施の最終日に不具合が見つかると、リリース日までに修正と確認をする時間がなくなります。
不具合は必ず出るものとして、最初から予定に入れておくほうが現実的だと思います。

終了日だけでなく、「何が終わったら次に進むか」をマイルストーンとして書いておくと、日付だけ過ぎて中身が終わっていない状態に気付けます。

### 3.2 体制と役割

> 誰がテストの責任者で、誰がテストを実施するのか（テスター）、不具合の修正は誰が行うのかといった役割分担を明確化

```md:記入例
## 3.2 体制と役割
| 役割 | 担当者 | 責任 |
| ---- | ---- | ---- |
| テスト責任者 | 佐藤（QA） | 本書の作成、完了基準の判定、リリース可否の報告 |
| テスト実施者 | 鈴木（QA）、田中（QA） | テストケースの実施、不具合の起票 |
| 不具合修正 | 高橋（アプリ）、伊藤（サーバ） | 不具合の調査・修正 |
| 仕様の確認先 | 渡辺（PdM） | 仕様に書かれていない挙動の判断 |
| リリース判断 | 山本（開発責任者） | テスト完了報告を受けてのリリース可否の決定 |
```

「QAチーム」のようなチーム名ではなく、担当者の名前を書きます。
チーム名だと、誰に聞けばよいのか結局分かりません。

役割の中でも抜けやすいのが「仕様の確認先」と「リリース判断」です。
仕様に書かれていない挙動を見つけたとき、テスト実施者が自分で正解を決めてしまわないよう、聞く相手を決めておきます。

### 3.3 成果物

> このテスト活動を通じて作成されるドキュメントの一覧を記述

```md:記入例
## 3.3 成果物
| 成果物 | 形式 | 置き場所 | レビュー担当 |
| ---- | ---- | ---- | ---- |
| テスト計画書（本書） | Markdown | `docs/テスト/2026-10-01_会員登録フロー改善/` | 山本 |
| テスト観点表 | TSV | 同上 | 佐藤、渡辺 |
| テスト手順書 | Markdown | 同上 | 佐藤 |
| 不具合報告 | GitHub Issue | `bug` ラベルを付けて起票 | 高橋、伊藤 |
| テスト完了報告書 | Markdown | `docs/テスト/2026-10-01_会員登録フロー改善/` | 山本 |
```

成果物の名前だけでなく、置き場所まで決めておきます。
置き場所が決まっていないと、テスト完了報告のときに「手順書はどこにありますか」から始まります。

テスト観点表とテスト手順書の書き方は、別の記事にまとめています。

@[card](https://zenn.dev/aew2sbee/articles/test-procedure-document)

## 🌱 4. テスト完了の基準

### 4.1 完了基準

> どのような状態になったらテストを完了とするのかを測定可能な形で具体的に定義

```md:記入例
## 4.1 完了基準
次のすべてを満たした時点で、テストを完了とする。

- テストケースの消化率が100%であること（「対象外」とした場合は理由が記載されていること）
- 未解決（修正・再テストが終わっていない）のクリティカルな不具合が0件であること
- 未解決のメジャーな不具合が1件以下であり、リリース後の対応予定日が決まっていること

不具合の重要度は、次のとおりに定義する。

| 重要度 | 定義 | 例 |
| ---- | ---- | ---- |
| クリティカル | 会員登録を完了できない。個人情報の漏えいや不正登録などのセキュリティ上の問題がある。会員データが不整合になる | SMS認証コードを入力しても登録が完了しない |
| メジャー | 登録は完了できるが、回避手順が必要になる | 認証コードの再送信ボタンが1回しか押せない |
| マイナー | 登録には影響しない表示や文言の問題 | エラーメッセージの句読点が他の画面と揃っていない |
```

「クリティカル」「メジャー」の定義を書いていないと、完了基準を満たしたかの判定でもめます。
同じ不具合でも、開発者は「回避できるからメジャー」、QAは「登録できない人がいるからクリティカル」と考えることがあるためです。

```diff text:完了基準の書き方
- 大きな不具合がないこと
+ 未解決のクリティカルな不具合が0件、未解決のメジャーな不具合が1件以下であること
```

「大きな不具合」は人によって大きさが変わり、測れません。
件数と、重要度の定義をセットで書きます。

### 4.2 中断・再開基準

> テストを一時的に中断せざるを得ない状況と、それを再開するための条件を定義

```md:記入例
## 4.2 中断・再開基準
| 中断する状況 | 再開する条件 |
| ---- | ---- |
| テスト環境にアクセスできない状態が2時間以上続く | テスト環境の復旧を、伊藤（サーバ）がSlackの `#shopnote-qa` で連絡する |
| アプリ側の不具合で会員登録を完了できない（固定値の認証コードでも回避できず、以降のテストケースがすべて実施できない） | 修正が反映され、会員登録の完了までを確認できる |
| テスト実施中に仕様変更が決まる | 変更後の仕様でテスト観点表を更新し、佐藤がレビューを終える |
```

中断する状況と、再開する条件は、1対1で書いておきます。

中断の基準だけ決めて再開の条件を決めていないと、「そろそろ直ったかな」と様子を見ながら何度も試すことになります。
再開の合図を誰がどこで出すのかまで書いておくと、待っている間に別の作業へ切り替えられます。

## 🌱 5. リスク管理

### 5.1 想定されるリスク / 5.2 予防策と対応策

> テスト活動を妨げる可能性のあるリスクを洗い出す

> 各リスクに対して「予防策」と、発生した場合の「対応策」を事前に検討

5.1 と 5.2 は、1つの表にまとめて書いています。
リスクと対策を別々の表にすると、どのリスクにどの対策が対応しているのかを行きつ戻りつして読むことになるためです。

```md:記入例
## 5.1 想定されるリスク / 5.2 予防策と対応策
| No. | リスク | 影響 | 予防策 | 対応策 |
| ---- | ---- | ---- | ---- | ---- |
| 1 | テスト実施中の仕様変更 | テストケースの作り直しが発生する | テスト設計のレビューに渡辺（PdM）を入れ、実施前に仕様を固める | 変更の影響範囲だけテストケースを更新し、重視度が高いものから実施する。期間内に終わらない場合は山本に報告する |
| 2 | 開発の遅延 | テスト実施の期間が短くなる | 画面ごとに、実装が終わった順にテストを始められるようテストケースを分けておく | 「2.3 テストで重視する観点」の重視度が高いテストケースから実施する |
| 3 | テスト担当者の急な不在 | テストケースを消化しきれない | テスト手順書を、担当者以外でも実施できる粒度で書く | 残りのテストケースを他の実施者に割り振る。足りない場合は開発メンバーに実施を依頼する |
| 4 | SMS送信サービスの送信上限 | SMS認証のテストが止まる | テスト用の電話番号と、送信上限の回数を事前に確認しておく | 認証コードを固定値にできるテスト用設定で、SMS認証以降のテストを進める |
```

対応策は、「頑張る」ではなく、実際に取れる行動で書きます。

```diff text:対応策の書き方
- 開発が遅延した場合は、残業して対応する
+ 開発が遅延した場合は、重視度が高いテストケースから実施する
```

残業で吸収する前提にすると、テストの時間が足りないときに削られるのは確認の丁寧さになります。
あらかじめ「どこから削るか」を決めておくと、時間が足りなくなっても重要な観点だけは確認できます。

:::message alert
SMS認証のテストでは、社員の個人の電話番号を使わないでください。
テスト用の電話番号を用意し、テストデータとして誰でも確認できる場所に置いておきます。
また、認証コードを固定値にする設定はテスト環境に限定し、本番環境では無効になっていることをリリース前に確認してください。
:::

## 🌱 おわりに

テンプレートを埋めてみて、一番時間がかかったのは「2.2 テスト対象外範囲」と「4.1 完了基準」でした。
どちらも、実際のプロジェクトでは関係者に確認して決める必要がある項目です。

テスト計画を書く作業の多くは、文書を書くことより「決まっていないことを見つけて決めてもらう」ことなのだと思います。

実際のプロジェクトで使うときは、まず次の3つから埋めようと思います。

- 対象外範囲に、理由を添えて書く
- 完了基準を、不具合の重要度の定義とセットで書く
- 中断する状況に、再開する条件を1対1で書く

この3つが決まっていれば、テストの途中で「どこまでやるのか」「いつ終わるのか」で迷う場面は減らせると思っています。
